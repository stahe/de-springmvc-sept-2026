    7. Der Lebenszyklus einer Anfrage

    Zwischen dem Eintreffen einer Anfrage und der Ausführung der Action sind mehrere Arten von Objekten beteiligt, jedes mit einer bestimmten Rolle. Einigen davon sind wir bereits begegnet: dem Handler für statische Dateien, [LocaleResolver] (Kapitel 5), dem Filter aus Beispiel 23, den Argument-Resolvern ([HandlerMethodArgumentResolver], Beispiel 12) und [@ControllerAdvice] (Beispiel 15). Es ist an der Zeit, sie zueinander in Beziehung zu setzen.

    Es gibt zwei Schichten. Die erste besteht aus dem Server ([Tomcat]) und dem Servlet-Standard ([Java]): Ein Servlet ist ein Objekt, das (HTTP-)Anfragen verarbeitet, und Servlet-Filter können es umhüllen, um davor und danach zu agieren. Die zweite Schicht ist [Spring MVC] selbst, das einfach ein Servlet ist, nämlich [DispatcherServlet]: Es wählt die Action aus, bindet ihre Parameter, führt sie aus und rendert dann die View. Innerhalb davon können Interceptors vor und nach der Action agieren. Während [ASP.NET Core] über Middleware und Filter (MVC) verfügt, [Spring] über Servlet-Filter und Interceptors verfügt. Die Fallstudie nutzt die meisten dieser Objekte:

    package example24.filters;

import java.io.IOException;

import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

// ein Servlet-FILTER: er sieht jede Anfrage VOR Spring MVC vorbeikommen und die
// Antwort NACH Spring MVC. @Component: Spring Boot fügt ihn der Filterkette hinzu.
@Component
public class LoggerFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain next)
            throws ServletException, IOException {
        String requestLine = request.getMethod() + " " + request.getRequestURI()
                + (request.getQueryString() == null ? "" : "?" + request.getQueryString());
        System.out.println();
        System.out.println("--- " + requestLine);
        System.out.println("1. filter (before)");
        next.doFilter(request, response); // der ganze Rest: Spring MVC, Action, View
        System.out.println("7. filter (after: code " + response.getStatus() + ")");
    }
}
    • Zeilen 15–16: ein Filter wie der in Beispiel 23. [OncePerRequestFilter] ist eine Unterklasse von [Spring] , die die Schnittstelle [Filter] des Servlet-Standards implementiert und eine einmalige Ausführung pro Anfrage sicherstellt; wir überschreiben ihre Methode [doFilterInternal], die bei jeder Anfrage aufgerufen wird. Mit [@Component] fügt [Spring Boot] den Filter der Filterkette des Servers hinzu;
    • Zeilen 21–22: die Methode, der Pfad und die Anfrageparameter. Der Filter weiß nichts über die Action, die die Anfrage verarbeiten wird: Er greift vor [Spring MVC] ein, das sie noch nicht ausgewählt hat;
    • Zeile 26: Der Filter übergibt die Anfrage an den Rest der Kette (die anderen Filter, dann [DispatcherServlet]) und wartet darauf, dass sie abgeschlossen ist. Würde er sie nicht aufrufen, würde die Anfrage dort enden (er müsste dann die Antwort selbst erzeugen). Der Code vor diesem Aufruf wird auf dem Hinweg ausgeführt, der Code danach auf dem Rückweg: Der Filter „umhüllt“ alles andere;
    • Zeile 27: auf dem Rückweg sieht der Filter den Statuscode der Antwort.

    package example24.filters;

import org.springframework.web.method.HandlerMethod;
import org.springframework.web.servlet.HandlerInterceptor;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

// ein INTERCEPTOR: er läuft innerhalb von Spring MVC, sobald die Action gewählt ist.
// Dieser entscheidet, ob die Action ausgeführt werden darf.
public class BlockInterceptor implements HandlerInterceptor {

    // preHandle: vor der Action; die Rückgabe von false beendet die Verarbeitung an dieser Stelle
    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler)
            throws Exception {
        // handler: was die Anfrage bearbeiten wird; bei einer Action ein HandlerMethod.
        // Anders als der Filter kennt der Interceptor also die anvisierte Action.
        if (handler instanceof HandlerMethod action && action.getBeanType().isAnnotationPresent(Block.class)) {
            System.out.println("2. Block interceptor (targeted action: " + action.getMethod().getName() + ")");
            if (request.getParameter("block") != null) {
                // eine Fehlerantwort 403 (Zugriff verweigert) und sonst nichts
                response.sendError(HttpServletResponse.SC_FORBIDDEN);
                return false; // weder Binding noch Action
            }
        }
        return true;
    }
}
    • Zeile 11: Ein Interceptor implementiert die Schnittstelle [HandlerInterceptor] von [Spring MVC]. Seine drei Methoden – [preHandle], [postHandle] und [afterCompletion] – haben eine Standardimplementierung, die nichts tut: Wir überschreiben nur diejenigen, die wir benötigen;
    • Zeile 15: [preHandle] wird vor der Action ausgeführt, sogar noch bevor ihre Parameter gebunden werden. Sein Parameter [handler], ist das, was die Anfrage verarbeiten wird: bei einer Action ein [HandlerMethod]-Objekt, das die Methode des Controllers beschreibt;
    • Zeile 19: Anders als der Filter weiß der Interceptor also, auf welche Action er zielt. [handler instanceof HandlerMethod action] prüft den Typ des Objekts und speichert es, falls er passt, in der Variablen [action], die den richtigen Typ hat. [getBeanType()] gibt die Klasse des Controllers an; [isAnnotationPresent(Block.class)] zeigt an, ob er die Annotation [@Block] trägt;
    • Zeilen 21–25: Ein Interceptor lehnt die Anfrage ab, indem er [false] zurückgibt: Der Rest des Ablaufs (Binding, Action, View) wird nicht ausgeführt. Er muss dann die Antwort selbst erzeugen: Hier erstellt [sendError(403)] eine Fehlerantwort „Zugriff verweigert“, für die der Server die Seite erzeugt (wir werden sehen, wie);
    • Zeile 27: [true]: Die Anfrage wird fortgesetzt.

    package example24.filters;

import org.springframework.web.method.HandlerMethod;
import org.springframework.web.servlet.HandlerInterceptor;
import org.springframework.web.servlet.ModelAndView;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

// ein zweiter Interceptor: er misst die Dauer der Verarbeitung
public class TimingInterceptor implements HandlerInterceptor {

    private static final String KEY = "timing";

    private static boolean concerned(Object handler) {
        return handler instanceof HandlerMethod action && action.getBeanType().isAnnotationPresent(Timing.class);
    }

    // vor der Action (und vor dem Binding ihrer Parameter)
    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        if (concerned(handler)) {
            System.out.println("3. Timing interceptor (before)");
            // die Startzeit, in einem Request-Attribut gespeichert (Request-Scope)
            request.setAttribute(KEY, System.nanoTime());
        }
        return true;
    }

    // nach der Action, VOR der View; wird nicht aufgerufen, wenn die Action eine Exception geworfen hat
    @Override
    public void postHandle(HttpServletRequest request, HttpServletResponse response, Object handler,
            ModelAndView mav) {
        if (concerned(handler)) {
            System.out.println("6a. Timing interceptor (after the action; chosen view: "
                    + (mav == null ? null : mav.getViewName()) + ")");
        }
    }

    // ganz am Ende, NACH der View; wird immer aufgerufen, mit der eventuellen Exception
    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler,
            Exception exception) {
        if (concerned(handler) && request.getAttribute(KEY) instanceof Long start) {
            long ms = (System.nanoTime() - start) / 1_000_000;
            String outcome = exception == null ? "" : ", exception " + exception.getClass().getSimpleName();
            System.out.println("6b. Timing interceptor (end, " + ms + " ms" + outcome + ")");
        }
    }
}
    • Zeilen 15–17: Der Interceptor interessiert sich nur für die Actions von Controllern, die mit [@Timing] annotiert sind;
    • Zeilen 21–28: Vor der Action wird die Startzeit ([System.nanoTime()], in Nanosekunden) erfasst und in einem Request-Attribut gespeichert (Request-Scope; siehe Kapitel 6);
    • Zeilen 32–38: [postHandle] läuft nach der Action und vor der View. Sie erhält das von der Action erzeugte [ModelAndView] (den Namen der View und das Modell) und kann es noch ändern. Sie wird nicht aufgerufen, wenn die Action eine Exception ausgelöst hat;
    • Zeilen 42–49: [afterCompletion] läuft ganz am Ende, nach der View, unabhängig davon, ob alles gut gegangen ist oder nicht: Dies ist der richtige Ort, um eine Ressource freizugeben oder die Ausführungszeit zu messen. Ihr letzter Parameter ist die Exception, falls vorhanden. Zeile 44: [instanceof Long start] prüft und konvertiert den Wert des Attributs in einem einzigen Schritt.

    package example24.filters;

import java.util.Map;

import org.springframework.core.MethodParameter;
import org.springframework.web.bind.support.WebDataBinderFactory;
import org.springframework.web.context.request.NativeWebRequest;
import org.springframework.web.context.request.RequestAttributes;
import org.springframework.web.method.support.HandlerMethodArgumentResolver;
import org.springframework.web.method.support.ModelAndViewContainer;
import org.springframework.web.servlet.HandlerMapping;

// das Binding eines Parameters @IntegerParam Integer: die gleichnamige Pfadvariable,
// in eine ganze Zahl konvertiert, oder null, wenn sie keine ganze Zahl ist
public class IntegerParamResolver implements HandlerMethodArgumentResolver {

    @Override
    public boolean supportsParameter(MethodParameter parameter) {
        return parameter.hasParameterAnnotation(IntegerParam.class) && parameter.getParameterType() == Integer.class;
    }

    @Override
    public Object resolveArgument(MethodParameter parameter, ModelAndViewContainer mavContainer,
            NativeWebRequest request, WebDataBinderFactory binderFactory) {
        // die Pfadvariablen ({n}...), von Spring in einem Request-Attribut gespeichert
        @SuppressWarnings("unchecked")
        Map<String, String> variables = (Map<String, String>) request.getAttribute(
                HandlerMapping.URI_TEMPLATE_VARIABLES_ATTRIBUTE, RequestAttributes.SCOPE_REQUEST);
        String value = variables == null ? null : variables.get(parameter.getParameterName());
        System.out.println("4. parameter binding (received value: \"" + value + "\")");
        try {
            return Integer.valueOf(value);
        } catch (NumberFormatException e) {
            return null; // die Action wird entscheiden
        }
    }
}

    Ein Argument-Resolver, wie der in Beispiel 12:

    • Zeilen 18–20: Er behandelt Parameter vom Typ [Integer] mit der Annotation [@IntegerParam];
    • Zeilen 27–28: [Spring MVC] hat den Pfad ([/square/{n}]) bei der Auswahl der Action bereits analysiert; es hat die Pfadvariablen in einem Request-Attribut in Form eines Dictionarys [name -> value] abgelegt;
    • Zeile 29: der Wert der Variablen, die wie der Parameter heißt ([n]);
    • Zeilen 31–35: der in eine ganze Zahl umgewandelte Wert oder [null] , wenn er keine ganze Zahl ist. Ein ungültiger Wert hält nichts auf: Die Action entscheidet.

    package example24.filters;

import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.ControllerAdvice;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.servlet.ModelAndView;

// @ControllerAdvice + @ExceptionHandler: eine von einer beliebigen Action geworfene
// Exception in eine Antwort umwandeln (hier für die gesamte Anwendung)
@ControllerAdvice
public class ErrorPageAdvice {

    // nur die IllegalStateException: die anderen Exceptions nehmen ihren Lauf
    @ExceptionHandler(IllegalStateException.class)
    public ModelAndView error(IllegalStateException e) {
        System.out.println("x. @ExceptionHandler (" + e.getClass().getSimpleName() + ": " + e.getMessage() + ")");
        // statt der Standard-Fehlerseite unsere View [error], mit dem Code 500
        ModelAndView mav = new ModelAndView("error", HttpStatus.INTERNAL_SERVER_ERROR);
        mav.addObject("code", 500);
        return mav;
    }
}
    • Zeile 10: [@ControllerAdvice] macht diese Klasse zu einer Ergänzung aller Controller (siehe Beispiel 15);
    • Zeilen 14–15: Eine [@ExceptionHandler]-Methode wird aufgerufen, wenn eine Action eine Exception des angegebenen Typs auslöst, hier [IllegalStateException] (oder eines abgeleiteten Typs). In einem Controller platziert, würde sie nur für die Actions dieses Controllers gelten; in einem [@ControllerAdvice] gilt sie für die gesamte Anwendung. Sie erhält die Exception als Parameter und erzeugt die Antwort genau wie eine Action;
    • Zeilen 18–20: Statt der Standard-Fehlerseite die View [error] mit dem Statuscode 500. Ein [ModelAndView] fasst zusammen, was eine Action üblicherweise in zwei Teilen zurückgibt: den Namen der View und das Modell (und hier den Statuscode).

    Die anderen Exceptions werden hier nicht behandelt: Was mit ihnen geschieht, sehen wir später.

// zwei am Controller gesetzte Annotationen: die Interceptors suchen nach ihnen
@Block
@Timing
@Controller
public class CalcController {

    @GetMapping("/square/{n}")
    public String square(@IntegerParam Integer n, Model model) {
        System.out.println("5. action square(" + n + ")");

}

    Bleibt die Fehlerseite. Wenn eine Anfrage in einer Fehlerantwort (einem Aufruf von [sendError], einer [ResponseStatusException], einer unbekannten Adresse oder einer unbehandelten Exception) endet, gibt der Server keine leere Antwort zurück: Er leitet die Anfrage an die Adresse [/error] weiter, um die zurückzugebende Seite zu erzeugen, und speichert dabei den Fehlercode in einem Request-Attribut. [Spring Boot] stellt für diese Adresse bereits eine Action bereit: Sie hat bisher die JSON-Fehlerantworten (für [curl]) und die „Whitelabel Error Page“ (für einen Browser) erzeugt.     package example24.controllers;

import org.springframework.boot.webmvc.error.ErrorController;
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.RequestMapping;

import jakarta.servlet.RequestDispatcher;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

// die Fehlerseite der Anwendung. Eine Fehlerantwort (sendError, unbehandelte
// Exception) wird vom Server an die Adresse /error weitergeleitet; die Implementierung
// von ErrorController ersetzt die Fehlerseite von Spring Boot durch unsere.
@Controller
public class ErrorPageController implements ErrorController {

    // @RequestMapping ohne HTTP-Methode: alle Methoden (GET, POST ...)
    @RequestMapping("/error")
    public String error(HttpServletRequest request, HttpServletResponse response, Model model) {
        // der ursprüngliche Fehlercode, vom Server in einem Request-Attribut gespeichert
        Object code = request.getAttribute(RequestDispatcher.ERROR_STATUS_CODE);
        int status = code instanceof Integer c ? c : 500;
        System.out.println("8. error page " + status + " (request forwarded to /error)");
        response.setStatus(status); // die Seite behält den Fehlercode
        model.addAttribute("code", status);
        return "error";
    }
}
    • Zeilen 15–16: ein Controller, der die Schnittstelle [ErrorController] von [Spring Boot] implementiert. Diese Schnittstelle hat keine Methoden; sie dient als Markierung. Sobald ein Bean sie implementiert, entfernt [Spring Boot] seinen eigenen Fehler-Handler;
    • Zeile 19: [@RequestMapping], das keine Methoden (HTTP) angibt, akzeptiert alle Methoden: Eine an [/error] weitergeleitete POST-Anfrage bleibt eine POST-Anfrage;
    • Zeilen 22–23: der ursprüngliche Fehlercode, vom Server im Attribut [RequestDispatcher.ERROR_STATUS_CODE] gespeichert. [code instanceof Integer c ? c : 500]: Wenn das Attribut eine ganze Zahl ist, deren Wert; andernfalls 500 (zum Beispiel, wenn [/error] direkt aufgerufen wird);
    • Zeilen 25–27: Die Seite behält den Fehlercode bei und übergibt ihn an die View.

    Dieses Protokoll zeigt:

    • die Reihenfolge der Schritte im Normalfall: der Filter, die Interceptors ([preHandle]) in der Reihenfolge ihres Hinzufügens, das Parameter-Binding, die Action, [postHandle] (die View ist noch nicht gerendert), [afterCompletion] (die View ist gerendert) und dann erneut der Filter, der den endgültigen Antwortcode sieht;
    • der Interceptor, der die Anfrage ablehnt ([/square/7?block=1]), umgeht alles andere in [Spring MVC]: kein zweiter Interceptor, kein Binding, keine Action;
    • Ein ungültiger Parameter verhindert die Ausführung der Action nicht: Die Action selbst entscheidet ([square(null)]), hier durch Auslösen einer [ResponseStatusException]. [Spring MVC] übergibt jede von einer Action ausgelöste Exception an eine Reihe von Exception-Handlern ([HandlerExceptionResolver]); derjenige der [ResponseStatusException] wandelt sie in eine Fehlerantwort 400 um und protokolliert sie (Zeile [WARN ... Resolved]). Da die Action eine Exception ausgelöst hat, wird [postHandle] nicht aufgerufen; [afterCompletion] wird ohne Exception aufgerufen: Die Exception wurde bereits behandelt;
    • die Exception von [/square/13] wird auf dieselbe Weise vom Resolver behandelt, der nach den [@ExceptionHandler]-Methoden sucht (Schritt x). Diese Methode erzeugt eine vollständige Seite mit dem Statuscode 500: Die Anfrage endet dort, ohne über [/error] zu laufen;
    • eine Fehlerantwort ohne Inhalt (400, 403, 404) wird in eine Seite umgewandelt, indem sie an [/error] weitergegeben wird (Schritt 8). Beachten Sie, dass dieser Schritt nach der Rückkehr der Anfrage zum Filter erfolgt (Schritt 7): [sendError] markiert die Antwort lediglich als Fehler, und es ist der Server ([Tomcat]), der die Anfrage nach Abschluss der Filterkette an [/error] weiterleitet. Dieser zweite Durchlauf geht nicht durch unseren Filter: [Spring Boot] registriert den Filter zwar für Anfragen, die an [/error] weitergeleitet werden, aber [OncePerRequestFilter] lässt sie passieren, ohne ihn auszuführen (dies ist sein Standardverhalten, das sich durch Überschreiben seiner Methode [shouldNotFilterErrorDispatch] ändern ließe). Er durchläuft jedoch die Interceptors, da es [Spring MVC] ist, das die Action [/error] ausführt; aber [ErrorPageController] trägt deren Annotationen nicht, und sie schreiben nichts;
    • Bei einer unbekannten Adresse passt keine Action: [Spring MVC] übergibt die Anfrage dann an den Handler für statische Dateien (einen [ResourceHttpRequestHandler]), der keine Datei findet und eine [NoResourceFoundException]-Exception auslöst, die von einem Exception-Resolver in eine Fehlerantwort 404 umgewandelt wird (diesmal ohne [WARN]-Zeile im Protokoll). Die Interceptors wurden zwar aufgerufen, aber der [handler], den sie erhielten, ist keine Action ([HandlerMethod]): Sie haben nichts geschrieben.
