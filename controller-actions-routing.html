    package example01;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

// @SpringBootApplication: diese Klasse ist der Startpunkt der Anwendung.
// Spring Boot sucht die Komponenten (Controller, Services ...) in seinem
// Paket [example01] und in allen Unterpaketen.
@SpringBootApplication
public class Example01Application {

    // die Java-main-Methode: der Einstiegspunkt des Programms
    public static void main(String[] args) {
        // wir starten Spring: Konfiguration, Erzeugung der Objekte, Tomcat-Webserver
        // (http://localhost:5000, siehe application.properties); Strg-C beendet ihn
        SpringApplication.run(Example01Application.class, args);
    }
}

    Gehen wir diesen Code durch:

    • Zeile 1: das Paket der Klasse. Es muss dem Verzeichnis der Datei entsprechen ([src/main/java/example01]);
    • Zeilen 3–4: Klassen aus anderen Paketen, die von dieser Datei verwendet werden. Anders als [C#] kennt [Java] keine impliziten Importe (außer für das Paket [java.lang], das [String], [Integer] ... enthält): Jede Datei importiert die von ihr verwendeten Klassen ausdrücklich;
    • Zeile 9: [@SpringBootApplication] ist eine Annotation. Eine [Java]-Annotation wird als [@Name] geschrieben, unmittelbar vor dem, was sie beschreibt (einer Klasse, einer Methode, einem Parameter ...): Sie fügt Informationen hinzu, die das Framework beim Start liest. Das entspricht den Attributen [[...]] in [C#]. [@SpringBootApplication] kennzeichnet die Startklasse der Anwendung und vereint drei Annotationen: [@Configuration] (die Klasse kann von [Spring] verwaltete Objekte deklarieren; siehe Beispiel 06), [@EnableAutoConfiguration] (Autokonfiguration: [Spring Boot] konfiguriert automatisch alles, was die verfügbaren Bibliotheken unterstützen, hier [Spring MVC], [Tomcat] und [Jackson]) und [@ComponentScan] (Komponentensuche: [Spring] sucht im Paket dieser Klasse, [example01], und in allen seinen Unterpaketen, etwa [example01.controllers], nach Klassen, die mit [@Controller], [@Service] ... annotiert sind);
    • Zeile 13: die Methode [main], der Einstiegspunkt jedes [Java]-Programms. Sie ist [public] (von überall sichtbar) und [static] (sie gehört zur Klasse, nicht zu einem Objekt der Klasse). Der Parameter [args] enthält die Kommandozeilenargumente;
    • Zeile 16: [SpringApplication.run] startet [Spring]: Es liest die Konfiguration (die Datei [application.properties], Umgebungsvariablen, Kommandozeilenargumente ...), erstellt die Objekte der Anwendung und startet dann den Webserver [Tomcat], der auf Anfragen wartet, bis die Anwendung beendet wird ([Ctrl-C]). [Example01Application.class] verweist auf die Klasse selbst: [Spring] liest daraus die Annotation [@SpringBootApplication] und leitet das zu durchsuchende Paket ab.

    Mehr ist nicht zu schreiben: keine Liste von Controllern, keine Routendeklarationen. Die Komponentensuche findet die Controller, und die Autokonfiguration richtet alles Übrige ein.

    package example01.controllers;

import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.ResponseBody;

// @Controller: diese Klasse ist ein Spring-MVC-Controller
@Controller
public class HomeController {

    // eine Action: die für die Anfrage GET / aufgerufene Methode
    @GetMapping("/")
    // @ResponseBody: der von der Action zurückgegebene Wert IST die an den Browser gesendete Antwort
    @ResponseBody
    public String index() {
        return "Hello from Spring MVC!";
    }
}
    • Zeile 1: Die Klasse liegt im Paket [example01.controllers], einem Unterpaket von [example01]: Die Komponentensuche findet sie;
    • Zeile 8: Die Annotation [@Controller] kennzeichnet die Klasse als Controller für [Spring MVC]. Die Klasse muss nicht von einer Framework-Klasse erben (das unterscheidet sich von [ASP.NET Core MVC]); ihr Name endet üblicherweise auf [Controller]. [Spring] erzeugt das Controller-Objekt beim Start selbst;
    • Zeile 12: Die Annotation [@GetMapping("/")] verknüpft die Methode [index] mit Anfragen vom Typ [GET /]. Eine auf diese Weise mit einer Route verknüpfte Methode ist eine Action;
    • Zeile 14: Die Annotation [@ResponseBody] legt fest, dass der von der Action zurückgegebene Wert der Body der an den Browser gesendeten Antwort ist. Ohne sie würde [Spring MVC] den zurückgegebenen String als Namen einer View behandeln, die angezeigt werden soll (das sehen wir in Beispiel 04 und dann in Kapitel 4);
    • Zeilen 15–16: Die Action gibt einen String zurück. Üblicherweise beginnen [Java]-Methodennamen mit einem Kleinbuchstaben.

    Die erste Zeile der Antwort ist der Statuscode 200, ohne den üblichen Text [OK]: [Tomcat] sendet ihn nicht, weil das HTTP-Protokoll ihn nicht verlangt. Der Browser und [curl] akzeptieren nur den Code.

    [curl] hat den String mit dem Header [Content-Type: text/plain] empfangen: reiner Text. Der Browser hat ihn jedoch als HTML dargestellt (erkennbar an der Schriftart, die der von HTML-Seiten entspricht). Das liegt daran, dass [Spring MVC] bei einem String, den eine Action ohne weitere Angaben zurückgibt, den Antworttyp anhand des Headers [Accept] der Anfrage wählt, mit dem der Client die akzeptierten Typen angibt: Das ist die Content Negotiation. [curl] sendet [Accept: */*] (alle Typen) und erhält [text/plain]; ein Browser sendet [Accept: text/html,...] und erhält [text/html].     package example02.controllers;

import org.springframework.http.MediaType;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

// @RestController = @Controller + @ResponseBody auf jeder Action
@RestController
public class HomeController {

    // GET /: eine HTML-Seite mit Links zu den anderen Actions.
    // produces: der Typ der Antwort (Content-Type-Header), hier HTML
    @GetMapping(value = "/", produces = MediaType.TEXT_HTML_VALUE)
    public String index() {
        return """
            <h2>Example 02 - routing</h2>
            <ul>
              <li><a href="/first">/first</a></li>
              <li><a href="/first/action01">/first/action01</a></li>
              <li><a href="/first/products/17">/first/products/17</a></li>
              <li><a href="/first/products/17/reviews/3">/first/products/17/reviews/3</a></li>
              <li><a href="/first/files/images/logo.png">/first/files/images/logo.png</a></li>
              <li><a href="/first/products/abc">/first/products/abc</a></li>
              <li><a href="/unknown">/unknown</a></li>
            </ul>
            """;
    }
}
    • Zeile 8: [@RestController] vereint [@Controller] und [@ResponseBody]: Alle Actions der Klasse geben direkt den Body der Antwort zurück. Das ist die gebräuchlichste Form für einen Controller, der keine Views erzeugt; wir verwenden sie bis Kapitel 4;
    • Zeile 13: Eine Annotation kann mehrere Attribute haben, geschrieben als [name = value]. [value] ist der Routenpfad (steht es allein, kann [value =] entfallen, wie in Beispiel 01); [produces] legt den Antworttyp fest (den Header [Content-Type]), hier [text/html], unabhängig vom Anfrage-Header [Accept]. [MediaType.TEXT_HTML_VALUE] ist eine Konstante, die gleich ["text/html"] ist: Ein Tippfehler in ihrem Namen würde einen Kompilierfehler verursachen, was bei einem von Hand geschriebenen String nicht der Fall ist;
    • Zeilen 15–26: ein Textblock ([text block], [Java] 15), begrenzt durch drei Anführungszeichen. Er kann sich über mehrere Zeilen erstrecken und Anführungszeichen enthalten, ohne dass sie maskiert werden müssen. Die allen seinen Zeilen gemeinsame Einrückung (einschließlich der des schließenden ["""]) wird entfernt.

    package example02.controllers;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

// Präfix, das alle Routen des Controllers gemeinsam haben
@RestController
@RequestMapping("/first")
public class FirstController {

    // GET /first
    @GetMapping("")
    public String index() {
        return "Action [index] of the [First] controller";
    }

    // GET /first/action01
    @GetMapping("/action01")
    public String action01() {
        return "Action [action01] of the [First] controller, GET request";
    }

    // POST /first/action01: gleicher Pfad, andere HTTP-Methode
    @PostMapping("/action01")
    public String action01Post() {
        return "Action [action01Post] of the [First] controller, POST request";
    }

    // GET /first/products/17: {id} ist eine Pfadvariable; \d+: nur Ziffern
    @GetMapping("/products/{id:\\d+}")
    public String product(@PathVariable int id) {
        return "Product no. " + id;
    }

    // GET /first/products/17/reviews/3: zwei Pfadvariablen
    @GetMapping("/products/{id:\\d+}/reviews/{number:\\d+}")
    public String review(@PathVariable int id, @PathVariable int number) {
        return "Review no. %d of product no. %d".formatted(number, id);
    }

    // GET /first/files/...: {*path} akzeptiert jedes beliebige Pfadende
    @GetMapping("/files/{*path}")
    public String file(@PathVariable String path) {
        return "Requested file: " + path;
    }
}

    Kommentieren wir diesen Code:

    • Zeilen 10–11: Die auf die Klasse angewandte Annotation ***[@RequestMapping("/first")]*** legt das allen Routen des Controllers gemeinsame Präfix fest: Seine Actions behandeln URL-Routen, die mit ***[/first]*** beginnen;
    • Zeilen 15–16: [@GetMapping("")]: Die Action [index] verarbeitet [GET /first]. Die URL einer Action ist die Verkettung des Controller-Präfixes und des Action-Pfads;
    • Zeilen 21–22: Die Action [action01] verarbeitet [GET /first/action01];
    • Zeilen 27–28: derselbe Pfad, aber für die Methode POST: [@PostMapping] ersetzt [@GetMapping]. Es gibt außerdem [@PutMapping], [@DeleteMapping], [@PatchMapping] ... (und [@RequestMapping], auf eine Methode angewandt, akzeptiert alle HTTP-Methoden). Der Name der [Java] -Methode ([action01Post]) ist beliebig: Für das Routing zählen nur die Annotationen. Außerdem können innerhalb derselben Klasse zwei Methoden nicht denselben Namen mit denselben Parametern haben;
    • Zeilen 33–34: [{id}] ist eine Pfadvariable: Dieses URL-Segment kann mehrere Werte annehmen. [\d+] ist ein regulärer Ausdruck: Das Segment muss aus einer oder mehreren Ziffern bestehen, andernfalls passt die Route nicht. In einem [Java]-String wird das Zeichen [\] als [\\] geschrieben: daher [{id:\\d+}]. Die Annotation [@PathVariable] weist [Spring MVC] an, den Wert des Segments an den gleichnamigen Parameter der Action zu übergeben, [id], nachdem er in [int] konvertiert wurde: Für [/first/products/17] ist [id] gleich der Zahl 17. Das ist das Datenbinding ([data binding]), das das nächste Kapitel im Detail behandelt. Damit [Spring] die Namen der Parameter kennt, muss der Compiler sie in den kompilierten Klassen erhalten (Option [-parameters]): [spring-boot-starter-parent] kümmert sich darum;
    • Zeile 35: Der Operator [+] verkettet einen String und eine Zahl;
    • Zeilen 39–41: Zwei Pfadvariablen werden als zwei Parameter an die Action übergeben. Die Methode [formatted] ersetzt jedes Vorkommen von [%d] im Text durch eine ganze Zahl, in der Reihenfolge der Argumente;
    • Zeilen 45–47: [{*path}] ist eine „Catch-all“-Variable ([catch-all]): Sie akzeptiert jedes URL-Ende, einschließlich [/]. Ihr Wert beginnt mit einem [/].

    package example03.controllers;

import java.time.Duration;
import java.time.Instant;
import java.util.List;
import java.util.Map;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.TimeUnit;

import org.springframework.http.HttpStatus;
import org.springframework.http.MediaType;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/responses")
public class ResponsesController {

    // ein String, als reiner Text angekündigt: der Browser zeigt ihn unverändert an
    @GetMapping(value = "/text", produces = MediaType.TEXT_PLAIN_VALUE)
    public String text() {
        return "<h1>Action [text]</h1>";
    }

    // derselbe String, als HTML angekündigt: der Browser interpretiert ihn
    @GetMapping(value = "/html", produces = MediaType.TEXT_HTML_VALUE)
    public String html() {
        return "<h1>Action [html]</h1>";
    }

    // ein Record: eine Datenklasse (siehe Beispiel 06), hier innerhalb des Controllers deklariert
    public record Person(String lastName, String firstName, int age) {
    }

    // ein Objekt: als JSON serialisiert, mit dem Typ [application/json]
    @GetMapping("/json")
    public Person json() {
        return new Person("Martin", "Jean", 42);
    }

    // eine Liste: als JSON-Array serialisiert
    @GetMapping("/list")
    public List<String> list() {
        return List.of("Mme", "Melle", "Mr");
    }

    // ResponseEntity: die Action wählt die vollständige Antwort (Code, Header, Inhalt)
    // status(201): der Code 201 (Created) statt 200 (OK)
    @GetMapping("/created")
    public ResponseEntity<Map<String, String>> created() {
        return ResponseEntity.status(HttpStatus.CREATED).body(Map.of("message", "resource created"));
    }

    // keine Antwort: der Code 204 (No Content) bedeutet "nichts anzuzeigen"
    @GetMapping("/empty")
    public ResponseEntity<Void> empty() {
        return ResponseEntity.noContent().build();
    }

    // eine asynchrone Action: Spring MVC wartet auf das Ende der Verarbeitung (CompletableFuture)
    @GetMapping("/task")
    public CompletableFuture<Map<String, String>> task() {
        Instant start = Instant.now();
        // eine Wartezeit von 500 ms, ohne den Thread zu blockieren, der die Anfrage erhalten hat
        return CompletableFuture.supplyAsync(
                () -> Map.of("wait", Duration.between(start, Instant.now()).toMillis() + " ms"),
                CompletableFuture.delayedExecutor(500, TimeUnit.MILLISECONDS));
    }

    // ein "erwarteter" Fehler: status(404) erzeugt eine 404-Antwort
    @GetMapping("/not-found")
    public ResponseEntity<Map<String, String>> notFound() {
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(Map.of("message", "This resource does not exist"));
    }

    // ein "unerwarteter" Fehler: eine unbehandelte Exception erzeugt eine 500-Antwort
    @GetMapping("/exception")
    public String exception() {
        throw new IllegalStateException("An unexpected error");
    }
}

    • Zeilen 28–31: derselbe String, als HTML deklariert: Der Browser interpretiert ihn;

    • Zeilen 51–54: Wenn die Action den Statuscode selbst bestimmen muss, gibt sie eine [ResponseEntity<T>] zurück: ein Objekt, das die vollständige Antwort beschreibt (Code, Header, Body vom Typ [T]).     • Zeilen 63–70: eine asynchrone Action. Sie gibt ein [CompletableFuture<T>] zurück, ein „ausstehendes“ Ergebnis (das Pendant zu einem [Task<T>] aus [C#] oder zu einem [JavaScript]-Promise); [Spring MVC] gibt den Thread von [Tomcat] , der die Anfrage bearbeitete, sofort frei und sendet die Antwort erst, wenn das Ergebnis vorliegt. [supplyAsync(function, executor)] berechnet das Ergebnis mit der Funktion, die hier nach einer Verzögerung von 500 ms ausgeführt wird. Die Funktion wird als Lambda geschrieben: [() -> expression] ist eine Funktion ohne Parameter, die den Wert des Ausdrucks zurückgibt. [Duration.between] misst die Zeitspanne zwischen zwei Zeitpunkten;
    • Zeilen 73–76: ein vom Programm vorhergesehener Fehler: eine [ResponseEntity] mit dem Code 404, die JSON enthält. Die Klasse [ResponseEntity] hat außerdem Kurzformen: [ok(...)] (200), [badRequest()] (400), [notFound()] (404) ...;
    • Zeilen 79–82: ein unerwarteter Fehler: Die Action wirft eine Exception, die sie nicht behandelt. [Spring Boot] antwortet dann mit einem Fehler 500 ([Internal Server Error]).

    package example04.controllers;

import java.net.URI;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.ResponseBody;
import org.springframework.web.servlet.mvc.support.RedirectAttributes;

// @Controller (und nicht @RestController): ein von einer Action zurückgegebener String ist
// hier der NAME EINER VIEW, und "redirect:..." ein spezieller View-Name
@Controller
public class RedirectsController {

    // permanente Weiterleitung (301): die Seite hat dauerhaft eine neue Adresse
    @GetMapping("/old")
    public ResponseEntity<Void> oldPage() {
        return ResponseEntity.status(HttpStatus.MOVED_PERMANENTLY).location(URI.create("/new")).build();
    }

    @GetMapping("/new")
    @ResponseBody
    public String newPage() {
        return "You are on the [new] page";
    }

    // temporäre Weiterleitung (302) auf eine berechnete Adresse
    @GetMapping("/go/{destination}")
    public String go(@PathVariable String destination) {
        return "redirect:/page/" + destination;
    }

    // Weiterleitung auf eine TEMPLATE-Adresse: Spring ersetzt {name} durch den Wert
    // des Attributs [name] und kodiert ihn korrekt für eine URL
    @GetMapping("/to-template/{destination}")
    public String toTemplate(@PathVariable String destination, RedirectAttributes attributes) {
        attributes.addAttribute("name", destination);
        return "redirect:/page/{name}";
    }

    @GetMapping("/page/{name}")
    @ResponseBody
    public String page(@PathVariable String name) {
        return "You are on the [" + name + "] page";
    }

    // Weiterleitung auf eine andere Website
    @GetMapping("/documentation")
    public String documentation() {
        return "redirect:https://docs.spring.io/spring-framework/reference/web/webmvc.html";
    }
}

    package example05.controllers;

import java.io.IOException;
import java.util.LinkedHashMap;
import java.util.Map;

import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

@RestController
@RequestMapping("/http")
public class HttpController {

    // die Anfrage: Methode, Pfad, Parameter, Header ...
    // Spring übergibt das Objekt HttpServletRequest an die Action, die es anfordert
    @GetMapping("/request")
    public Map<String, String> request(HttpServletRequest request) {
        // LinkedHashMap: ein Dictionary, das die Einfügereihenfolge der Schlüssel beibehält
        Map<String, String> info = new LinkedHashMap<>();
        info.put("method", request.getMethod());
        info.put("path", request.getRequestURI());
        info.put("parameters", request.getQueryString());
        info.put("browser", request.getHeader("User-Agent"));
        info.put("ip", request.getRemoteAddr());
        return info;
    }

    // die Antwort: wir fügen ihr einen Header hinzu, dann gibt die Action ihren Wert ganz normal zurück
    @GetMapping("/header")
    public String header(HttpServletResponse response) {
        response.setHeader("X-Example", "05-request-response");
        return "Response with an added header";
    }

    // die Antwort "von Hand" geschrieben: Code, Typ, dann der Body
    @GetMapping("/response")
    public void response(HttpServletResponse response) throws IOException {
        response.setStatus(200);
        response.setContentType("text/plain;charset=UTF-8");
        response.getWriter().write("Response written by [response.getWriter()]");
    }

    // FEHLER, den man nicht machen darf: die Antwort schreiben und DANN ein Ergebnis zurückgeben
    @GetMapping("/double")
    public ResponseEntity<Void> doubleResponse(HttpServletResponse response) throws IOException {
        response.getWriter().write("Start of the response... ");
        // flushBuffer: die ersten Bytes gehen an den Browser
        response.flushBuffer();
        // die Antwort ist bereits gesendet: Code und Header können sich nicht mehr ändern
        return ResponseEntity.notFound().build();
    }
}

    Kommentieren wir diesen Code:

    • Zeilen 12–13: Die Klassen der API [Servlet] liegen im Paket [jakarta.servlet...];
    • Zeile 22: Die Action deklariert einen Parameter vom Typ [HttpServletRequest]: [Spring MVC] übergibt ihr die aktuelle Anfrage. So stellt [Spring MVC] einer Action bereit, was sie braucht: anhand des Typs ihrer Parameter oder anhand ihrer Annotationen ([@PathVariable] ...);
    • Zeile 24: ein veränderbares Dictionary. [Map] ist ein Interface (ein Typ, der Operationen beschreibt, ohne sie zu implementieren; wir kommen in Beispiel 06 darauf zurück), [LinkedHashMap] ist eine seiner Implementierungen; [<>] übernimmt die generischen Typen aus der Deklaration ([<String, String>]);
    • Zeilen 25–29: die Anfrage: die HTTP-Methode ([getMethod]), der Pfad ([getRequestURI]), die URL-Parameter ([getQueryString], ohne das [?], oder [null] , falls keine vorhanden sind), ein Header ([getHeader]) und die IP-Adresse des Clients ([getRemoteAddr]);
    • Zeilen 34–38: Die Action fügt der Antwort einen Header hinzu und gibt dann normal seinen Wert zurück, den [Spring MVC] sendet. Das ist die häufigste Verwendung des Response-Objekts;
    • Zeilen 41–46: Die Action schreibt die Antwort selbst – Statuscode, Typ und dann den Body – mit dem Objekt [PrintWriter], das [getWriter()] liefert. Sie gibt nichts zurück ([void]): [Spring MVC] geht dann davon aus, dass die Antwort von der Action geschrieben wurde. Die Klausel [throws IOException] deklariert, dass die Methode eine [IOException] (einen Schreibfehler) werfen kann: In [Java] muss eine Methode auf diese Weise die sogenannten geprüften Exceptions deklarieren, die sie nicht behandelt;
    • Zeilen 49–56: der zu vermeidende Fehler: einen Teil der Antwort zu schreiben und dann ein Ergebnis zurückzugeben. Sobald die ersten Bytes des Bodys an den Browser gesendet wurden (hier erzwungen durch [flushBuffer]), können Statuscode und Header – die vor dem Body gesendet werden – nicht mehr geändert werden.

    Ein Record (siehe Beispiel 03), diesmal in einer eigenen Datei. Der Typ [BigDecimal] stellt Beträge ohne Rundungsfehler dar, was der Typ [double] nicht garantiert.

    package example06.products;

import java.util.List;
import java.util.Optional;

// der VERTRAG des Services: was er kann, ohne zu sagen, wie
public interface ProductsService {

    List<Product> findAll();

    Optional<Product> findById(int id);
}
    • Zeile 7: Ein Interface beschreibt, was der Service kann, ohne festzulegen, wie. Klassen, die den Service verwenden, kennen nur dieses Interface. Anders als die Konvention in [C#] ([IProductsService]) beginnt der Name eines [Java] -Interfaces nicht mit [I];
    • Zeile 9: [List<Product>]: eine Liste von Produkten;
    • Zeile 11: [Optional<Product>]: ein Produkt, oder nichts , wenn kein Produkt diese Kennung hat. Ein [Optional] ist ein Behälter, entweder leer oder mit einem Wert: Er zwingt den Aufrufer, den Fall zu bedenken, dass es kein Produkt gibt, während ein [null] übersehen werden könnte (und eine [NullPointerException] verursachen würde).

    package example06.products;

import java.math.BigDecimal;
import java.util.List;
import java.util.Optional;

// eine IMPLEMENTIERUNG des Vertrags: hier mit Daten im Speicher
public class InMemoryProductsService implements ProductsService {

    private final List<Product> products = List.of(
            new Product(1, "pen", new BigDecimal("1.5")),
            new Product(2, "notebook", new BigDecimal("3.2")),
            new Product(3, "eraser", new BigDecimal("0.8")));

    @Override
    public List<Product> findAll() {
        return products;
    }

    @Override
    public Optional<Product> findById(int id) {
        return products.stream().filter(p -> p.id() == id).findFirst();
    }
}
    • Zeile 8: Die Klasse implementiert das Interface ([implements]): Sie muss alle seine Methoden bereitstellen;
    • Zeilen 10–13: die Daten, hier im Speicher, in einer schreibgeschützten Liste. Die Beträge werden aus Strings erzeugt: [new BigDecimal("1.5")] ist exakt 1,5;
    • Zeilen 15 und 20: Die Annotation [@Override] zeigt an, dass die Methode zu einem Interface (oder einer Elternklasse) gehört: Der Compiler prüft, ob sie dort tatsächlich existiert;
    • Zeile 22: ein Iterator ([stream]) durchläuft die Liste: [filter] behält nur die Produkte, die die Bedingung erfüllen, geschrieben als Lambda mit einem Parameter (siehe Beispiel 03), [p]; [findFirst] gibt das erste verbleibende Produkt in einem [Optional] zurück, das leer ist, wenn keines übrig bleibt. [p.id()] ist die Zugriffsmethode für die Komponente [id] des Records.

    Die Klasse hat keine Annotationen: Sie ist eine gewöhnliche [Java]-Klasse, die nichts von [Spring] weiß. Wie sie zu einer Bean wird, sehen wir gleich.

    package example06.products;

import java.util.List;
import java.util.Map;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/products")
public class ProductsController {

    private final ProductsService productsService;

    // Dependency Injection: Spring stellt die Implementierung von ProductsService bereit
    public ProductsController(ProductsService productsService) {
        this.productsService = productsService;
    }

    @GetMapping("")
    public List<Product> list() {
        return productsService.findAll();
    }

    @GetMapping("/{id:\\d+}")
    public ResponseEntity<?> oneProduct(@PathVariable int id) {
        return productsService.findById(id)
                .<ResponseEntity<?>>map(ResponseEntity::ok)
                .orElseGet(() -> ResponseEntity.status(HttpStatus.NOT_FOUND)
                        .body(Map.of("message", "Product no. " + id + " not found")));
    }
}
    • Zeilen 17–22: Dependency Injection. Der Controller deklariert in seinem Konstruktor, dass er einen [ProductsService] benötigt; [Spring], das den Controller erzeugt, stellt ihm eine Bean dieses Typs bereit (siehe unten). Der Controller ruft nie [new InMemoryProductsService()] auf: Er kennt diese Klasse nicht einmal, nur das Interface. Wir könnten die Implementierung ersetzen (durch eine Version, die eine Datenbank liest, oder durch eine Testversion), ohne den Controller zu ändern. Das Feld ist als ***[final]*** deklariert: Es kann nur einmal zugewiesen werden, im Konstruktor;
    • Zeilen 24–27: Die Action delegiert an den Service. Die Liste wird als JSON serialisiert;
    • Zeilen 29–35: [{id:\\d+}] akzeptiert nur Zahlen; ein nicht vorhandenes Produkt liefert eine Antwort 404. Das vom Service zurückgegebene [Optional] wird in zwei Schritten verarbeitet: [map] wandelt seinen Inhalt, falls vorhanden, in eine Antwort 200 um; [orElseGet] liefert die Antwort, die verwendet wird, wenn das [Optional] leer ist – hier eine Antwort 404 mit einer Meldung. [ResponseEntity::ok] ist eine Methodenreferenz: eine kürzere Schreibweise für das Lambda [p -> ResponseEntity.ok(p)]. Der Typ [ResponseEntity<?>] ([?]: beliebiger Body-Typ) erlaubt es der Action, ein Produkt oder ein Dictionary zurückzugeben; die Schreibweise [.<ResponseEntity<?>>map(...)] teilt dem Compiler diesen Typ mit, den er nicht selbst ableiten kann.

    package example06.clients;

import java.math.BigDecimal;
import java.util.List;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

import example06.products.Product;
import example06.products.ProductsService;

// ein einziger Konstruktor: Spring verwendet ihn für die Injektion, ganz ohne weiteren Hinweis.
// Das Feld [final] ist daher zwangsläufig initialisiert.
@RestController
@RequestMapping("/clients")
public class ClientsController {

    private final ProductsService productsService;

    public ClientsController(ProductsService productsService) {
        this.productsService = productsService;
    }

    // der Inhalt des Warenkorbs, als JSON zurückgegeben
    public record Cart(String client, int items, BigDecimal total) {
    }

    @GetMapping("/cart")
    public Cart cart() {
        List<Product> products = productsService.findAll();
        // die Summe der Preise: map (transformieren), dann reduce (akkumulieren)
        BigDecimal total = products.stream().map(Product::price).reduce(BigDecimal.ZERO, BigDecimal::add);
        return new Cart("Jean Martin", products.size(), total);
    }
}
    • Zeilen 19–23: [ClientsController] erhält denselben Service wie [ProductsController]. Die Klasse hat nur einen Konstruktor: [Spring] verwendet ihn ohne weitere Angaben für die Injektion. Das ist die empfohlene Form der Injektion und die im gesamten Dokument verwendete;
    • Zeilen 26–27: ein verschachtelter Record, der die JSON-Antwort beschreibt;
    • Zeile 33: die Berechnung der Summe. [map] wandelt den Stream der Produkte in einen Stream der Preise um ([Product::price] ist ein Verweis auf die Zugriffsmethode [price()] des Records), dann akkumuliert [reduce] sie, ausgehend von null ([BigDecimal.ZERO]) und indem es sie paarweise addiert ([BigDecimal::add]).

    2.6.6. Beans deklarieren

    [Spring] kann einen Service nur bereitstellen, wenn es ihn kennt: Jeder Service muss als Bean deklariert werden. Controller werden über ihre Annotation [@RestController] deklariert, die bei der Komponentensuche erkannt wird (siehe Beispiel 01). Die Klasse [InMemoryProductsService] hingegen hat keine Annotation: Sie wird in der Datei [products/ProductsConfig.java] deklariert:

    package example06.products;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

// eine KONFIGURATIONSklasse: ihre @Bean-Methoden erzeugen Objekte, die Spring
// verwaltet ("Beans") und denen bereitstellt, die sie benötigen. Sie bündelt
// die Deklarationen des Teils "Produkte" der Anwendung.
@Configuration
public class ProductsConfig {

    // "wenn ein ProductsService angefordert wird, DIESES Objekt bereitstellen"; standardmäßig ist
    // eine Bean ein Singleton: eine einzige Instanz, von allen Anfragen gemeinsam genutzt
    @Bean
    public ProductsService productsService() {
        return new InMemoryProductsService();
    }
}
    • Zeile 9: Die Annotation [@Configuration] kennzeichnet die Klasse als Konfigurationsklasse; auch sie wird bei der Komponentensuche gefunden, und [Spring] führt beim Start ihre mit [@Bean] annotierten Methoden aus. Sie bündelt die Deklarationen für den Teil „Produkte“ der Anwendung;
    • Zeilen 14–17: Eine Methode, die mit [@Bean] annotiert ist, erzeugt eine Bean. Das bedeutet: „Wenn eine Klasse einen [ProductsService] anfordert, stelle ihr das Objekt bereit, das diese Methode zurückgibt.“ Der Methodenname ([productsService]) wird zum Namen der Bean.

    Es gibt eine weitere, kürzere Möglichkeit, eine Bean zu deklarieren: die Klasse selbst mit [@Service] (oder [@Component], wovon [@Service], [@Controller] und [@Repository] Varianten sind) zu annotieren, was die Komponentensuche genauso findet wie Controller. Würde man [@Service] vor die Klasse [InMemoryProductsService] setzen, wäre die Datei [ProductsConfig.java] überflüssig. Die Methode mit [@Bean] ist nützlich, wenn die Klasse keine Annotation tragen kann (etwa eine Klasse aus einer Bibliothek) oder wenn zur Erzeugung des Objekts Code nötig ist. Beide Formen werden später in diesem Dokument verwendet.

    Standardmäßig ist eine Bean ein Singleton: [Spring] erzeugt beim Start eine einzige Instanz und stellt sie während der gesamten Laufzeit der Anwendung allen Klassen bereit, die sie anfordern. [ProductsController] und [ClientsController] erhalten somit dasselbe [InMemoryProductsService]-Objekt. Es gibt weitere Scopes: [prototype] (eine neue Instanz bei jeder Anforderung), [request] (eine Instanz pro HTTP-Anfrage), [session] ... Kapitel 6 greift dieses Thema wieder auf.

    Auch Controller sind Singletons: Ein einziges [ProductsController]-Objekt bearbeitet alle Anfragen, möglicherweise gleichzeitig in mehreren Threads. Das ist ein wesentlicher Unterschied zu [ASP.NET Core MVC], das für jede Anfrage ein neues Controller-Objekt erzeugt. Ein [Spring]-Controller darf daher keine anfragespezifischen Daten in seinen Feldern speichern: Seine Felder enthalten nur die injizierten Services, deklariert als [final].

    Die Klasse [Example06Application] ist dieselbe wie in den vorherigen Beispielen: Dort muss nichts registriert werden; die Komponentensuche findet die Controller und die Konfigurationsklasse in den Unterpaketen [clients] und [products].
