    9. Schichtenarchitektur und Datenzugriff

    Die vorherigen Beispiele speicherten ihre Daten im Speicher. Eine reale Anwendung speichert sie in einer Datenbank und ist in Schichten gegliedert (siehe das Diagramm in der Einführung):

    • die Web-Schicht (Controller, Views): liest die Anfrage, ruft die Geschäftsschicht auf, wählt die View aus;
    • die Geschäftsschicht: Geschäftsregeln;
    • die DAO-Schicht ([Data Access Object]): Datenbankabfragen.

    Jede Schicht kennt nur die darunterliegende Schicht, und von dieser so wenige Details wie möglich: Die Web-Schicht kennt kein SQL, und die Geschäftsschicht kennt kein HTML. Diese Trennung macht jede Schicht leichter verständlich, testbar und weiterentwickelbar. Beispiel 28 wendet dies auf die Verwaltung einer Personenliste an: Es ist, in kleinerem Maßstab, die Verwaltung der Ärzte und Klienten der Fallstudie.

    In [Java] ist der Datenbankzugriff auf mehrere Schichten verteilt:

    • [JDBC] ([Java Database Connectivity]) ist die Standardschnittstelle, mit der [Java] SQL-Befehle an eine Datenbank sendet. Jedes Datenbankverwaltungssystem stellt einen Treiber [JDBC] bereit: für [MySQL] ist es die Bibliothek [mysql-connector-j]. Das Öffnen einer Verbindung ist ressourcenintensiv: [Spring Boot] verwendet einen Connection-Pool ([HikariCP]), der einige Verbindungen offen hält und sie an Anfragen verleiht;
    • [JPA] ([Jakarta Persistence API]) ist der Standard für [Java] im Bereich ORM ([Object-Relational Mapper]): Er bildet [Java]-Klassen (Entitäten) auf Datenbanktabellen ab und wandelt die gelesenen Zeilen in Objekte um. [JPA] ist lediglich ein Standard, bestehend aus Schnittstellen und Annotationen; das ORM, das ihn implementiert, ist hier [Hibernate];
    • [Spring Data JPA] wird darauf aufgesetzt: Sie müssen lediglich eine DAO-Schnittstelle deklarieren, und [Spring Data JPA] schreibt die Implementierung beim Start der Anwendung selbst, einschließlich der Abfragen, die es aus den Methodennamen ableitet.

    Dies alles stellt der Starter [spring-boot-starter-data-jpa] bereit.

-- das Skript ist in UTF-8 geschrieben
SET NAMES utf8mb4;
DROP DATABASE IF EXISTS dbpersons;
CREATE DATABASE dbpersons CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE dbpersons;

CREATE TABLE persons (
  id INT NOT NULL AUTO_INCREMENT,
  -- die Version der Zeile, bei jeder Änderung von JPA erhöht
  version INT NOT NULL DEFAULT 0,
  first_name VARCHAR(30) NOT NULL,
  last_name VARCHAR(30) NOT NULL,
  age INT NOT NULL,
  PRIMARY KEY (id),
  -- zwei Personen dürfen nicht denselben Vor- und Nachnamen haben
  CONSTRAINT unq_persons_first_name_last_name UNIQUE (first_name, last_name)
) ENGINE = InnoDB;

INSERT INTO persons (first_name, last_name, age) VALUES
  ('Marie', 'Pélissier', 42),
  ('Jacques', 'Bromard', 35),
  ('Philippe', 'Jandot', 58);
    • Zeile 3: Das Skript ist in UTF-8 geschrieben; dies wird dem Server mitgeteilt, damit die Akzente in den Daten ([Pélissier]) erhalten bleiben;

    package example28.entities;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.Version;

// eine Zeile der Tabelle [persons]
@Entity
@Table(name = "persons")
public class Person {

    // der Primärschlüssel, von der Datenbank erzeugt (AUTO_INCREMENT); JPA liest seinen
    // Wert nach jedem INSERT erneut
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @Column(name = "id")
    private Integer id;

    // optimistisches Sperren: JPA erhöht die Version bei jedem UPDATE und fügt
    // die Bedingung "AND version = <gelesener Wert>" hinzu
    @Version
    @Column(name = "version")
    private Integer version;

    @Column(name = "first_name", length = 30)
    private String firstName;

    @Column(name = "last_name", length = 30)
    private String lastName;

    @Column(name = "age")
    private int age;

    // ein Konstruktor ohne Parameter wird von JPA benötigt
    public Person() {
    }

    public Person(String firstName, String lastName, int age) {
        this.firstName = firstName;
        this.lastName = lastName;
        this.age = age;
    }

    public Integer getId() { return id; }

    public Integer getVersion() { return version; }

    public String getFirstName() { return firstName; }
    public void setFirstName(String firstName) { this.firstName = firstName; }

    public String getLastName() { return lastName; }
    public void setLastName(String lastName) { this.lastName = lastName; }

    public int getAge() { return age; }
    public void setAge(int age) { this.age = age; }
}
    • Zeile 12: [@Entity] erzeugt eine [JPA] -Entität aus der Klasse [Person]: Jede Zeile der Tabelle wird zu einem [Person]-Objekt. Die Annotationen stammen aus dem Paket [jakarta.persistence]: Es sind die aus dem Standard [JPA], nicht die von [Hibernate];
    • Zeile 13: die zugehörige Tabelle (standardmäßig wäre dies [Person]);
    • Zeilen 18–21: der Primärschlüssel ([@Id]). [@GeneratedValue(strategy = GenerationType.IDENTITY)] gibt an, dass sein Wert von der Datenbank vergeben wird ([AUTO_INCREMENT]): [Hibernate] liest den vergebenen Wert nach jedem [INSERT] aus. Der Typ [Integer] – nicht [int] – erlaubt den Wert [null]: Eine Person, die noch nicht gespeichert wurde, hat keine ID. [@Column] gibt den Spaltennamen an, der dem jeweiligen Feld entspricht;
    • Zeilen 25–27: die Versionsspalte. [@Version] überträgt die optimistische Sperre an [Hibernate]: Es setzt die Version beim [INSERT] auf 0, erhöht sie bei jedem [UPDATE] um 1 und fügt die Bedingung [AND version = <value read>] bei jedem [UPDATE] (und bei jedem [DELETE]) hinzu. Wozu das dient, sehen wir später;
    • Zeilen 29–36: die übrigen Spalten. [length] legt die Spaltenbreite fest: Sie wäre nur relevant, wenn [Hibernate] die Tabelle selbst erstellen würde, was hier nicht der Fall ist (siehe [ddl-auto]);
    • Zeilen 39–40: [JPA] verlangt einen parameterlosen Konstruktor: Es ist derjenige, den [Hibernate] verwendet, um aus einer gelesenen Zeile ein Objekt zu erzeugen, bevor es seine Felder befüllt;
    • Zeilen 48–59: die Zugriffsmethoden (Methoden [getX] und [setX]): Die Entität ist eine JavaBean. Es gibt kein [setId] und kein [setVersion]: Diese beiden Werte werden nur von [Hibernate] geschrieben, das direkt auf die Felder zugreift.

    package example28.dao;

import java.util.List;
import java.util.Optional;

import org.springframework.data.jpa.repository.JpaRepository;

import example28.entities.Person;

// die DAO-Schicht: Abfragen, keine Geschäftsregel.
// Ein Interface, das Spring Data JPA beim Start selbst IMPLEMENTIERT.
// JpaRepository<Person, Integer> bringt bereits findById, save, deleteById ... mit
public interface PersonsDao extends JpaRepository<Person, Integer> {

    // der Name der Methode beschreibt die Abfrage:
    // SELECT ... FROM persons ORDER BY last_name, first_name
    List<Person> findAllByOrderByLastNameAscFirstNameAsc();

    // eine Person mit gleichem Vor- und Nachnamen, außer [exceptId]:
    // SELECT ... WHERE first_name = ? AND last_name = ? AND id <> ? LIMIT 1
    Optional<Person> findFirstByFirstNameAndLastNameAndIdNot(String firstName, String lastName, Integer exceptId);
}

    Dies ist die gesamte DAO-Schicht: eine Schnittstelle ohne eine einzige Zeile ausführbaren Codes.

    • Zeile 13: Die Schnittstelle erbt von [JpaRepository<Person, Integer>] (eine Entität [Person], deren Schlüssel ein [Integer] ist). Beim Start erzeugt [Spring Data JPA] eine Klasse, die diese Schnittstelle implementiert, und macht sie zu einem Bean, das anschließend injiziert wird. [JpaRepository] stellt bereits die Standardmethoden bereit: [findById] (Lesen über den Schlüssel, Ergebnis in einem [Optional]), [findAll], [save] ([INSERT] oder [UPDATE]), [saveAndFlush], [deleteById], [count] ...;
    • Zeile 17: eine abgeleitete Abfrage: [Spring Data JPA] analysiert den Methodennamen und leitet daraus die Abfrage ab. [findAll]: alle Personen; [By]: ohne Bedingungen, da nichts folgt; [OrderByLastNameAscFirstNameAsc]: sortiert nach Nachname, dann nach Vorname, jeweils aufsteigend;
    • Zeile 21: [findFirst]: die erste gefundene Person ([LIMIT 1]) oder ein leeres [Optional]; [ByFirstNameAndLastNameAndIdNot]: deren Vor- und Nachname mit den als Parametern übergebenen übereinstimmen und deren ID sich vom dritten Parameter unterscheidet. Das ist nützlich beim Ändern eines Datensatzes, der nicht mit sich selbst in Konflikt geraten darf. Der Vergleich wird von [MySQL] durchgeführt und folgt somit den Kollationsregeln der Datenbank: Er ignoriert Groß-/Kleinschreibung und Akzente.

    Ein Fehler in einem Methodennamen ([findAllByOrderByLastNamee]) wird beim Start erkannt: Die Anwendung verweigert den Start und meldet eine unbekannte Eigenschaft. Eine für einen Methodennamen zu komplexe Abfrage wird in der Sprache [JPQL] ([Jakarta Persistence Query Language], ein SQL, das sich auf Entitäten und ihre Felder statt auf Tabellen bezieht), in einer Annotation [@Query] geschrieben: Die Fallstudie verwendet einige davon.

    package example28.business;

import java.util.List;
import java.util.Objects;

import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.orm.ObjectOptimisticLockingFailureException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import example28.dao.PersonsDao;
import example28.entities.Person;

// die GESCHÄFTSSCHICHT: die Geschäftsregeln, und nur sie.
// @Transactional auf der Klasse: jede öffentliche Methode läuft in einer
// Transaktion, die am Ende der Methode bestätigt (COMMIT) und, wenn
// sie eine Exception wirft, abgebrochen wird (ROLLBACK)
@Service
@Transactional
public class PersonsBusiness {

    private static final String NAMESAKE = "A person already has these first and last names.";
    private static final String MODIFIED = "This record has been modified meanwhile: reload it.";

    private final PersonsDao dao;

    public PersonsBusiness(PersonsDao dao) {
        this.dao = dao;
    }

    // readOnly: eine schreibgeschützte Transaktion
    @Transactional(readOnly = true)
    public List<Person> list() {
        return dao.findAllByOrderByLastNameAscFirstNameAsc();
    }

    @Transactional(readOnly = true)
    public Person read(int id) {
        return dao.findById(id).orElseThrow(() -> new BusinessException("This person does not exist (anymore)."));
    }

    public Person add(PersonData data) {
        // Regel 1: keine zwei Personen mit gleichem Vor- und Nachnamen
        if (dao.findFirstByFirstNameAndLastNameAndIdNot(data.firstName(), data.lastName(), 0).isPresent()) {
            throw new BusinessException(NAMESAKE);
        }
        return save(new Person(data.firstName(), data.lastName(), data.age()));
    }

    public Person edit(int id, Integer version, PersonData data) {
        Person person = read(id);
        // Regel 2: wir ändern keinen Datensatz, der inzwischen von jemand anderem geändert wurde
        if (!Objects.equals(person.getVersion(), version)) {
            throw new BusinessException(MODIFIED);
        }
        if (dao.findFirstByFirstNameAndLastNameAndIdNot(data.firstName(), data.lastName(), id).isPresent()) {
            throw new BusinessException(NAMESAKE);
        }
        // die gelesene Entität wird von JPA "verfolgt": sie zu ändern genügt
        person.setFirstName(data.firstName());
        person.setLastName(data.lastName());
        person.setAge(data.age());
        return save(person);
    }

    public Person delete(int id) {
        Person person = read(id);
        dao.deleteById(id);
        return person;
    }

    // saveAndFlush: INSERT oder UPDATE wird SOFORT an die Datenbank gesendet (und nicht beim
    // COMMIT), um die Datenbankfehler hier abfangen zu können
    private Person save(Person person) {
        try {
            return dao.saveAndFlush(person);
        } catch (ObjectOptimisticLockingFailureException e) {
            // das UPDATE "WHERE id = ... AND version = ..." hat keine Zeile geändert
            throw new BusinessException(MODIFIED);
        } catch (DataIntegrityViolationException e) {
            // zwei gleichzeitige Hinzufügungen: der Eindeutigkeits-Constraint der Datenbank hat die zweite abgelehnt
            if (String.valueOf(e.getMostSpecificCause().getMessage()).contains("unq_persons_first_name_last_name")) {
                throw new BusinessException(NAMESAKE);
            }
            throw e;
        }
    }
}

    Kommentieren wir diesen Code:

    • Zeile 18: Die Geschäftsschicht ist ein Service-Bean;
    • Zeile 19: [@Transactional], an der Klasse angebracht, gilt für jede ihrer öffentlichen Methoden: Die Methode wird innerhalb einer Transaktion ausgeführt, die vor ihrem Aufruf geöffnet ([START TRANSACTION]), bei ihrer Rückkehr festgeschrieben ([COMMIT]) und zurückgerollt ([ROLLBACK]) wird, wenn sie eine ungeprüfte Exception auslöst. Wie bei [@PreAuthorize] (Beispiel 26) umhüllt [Spring] das Bean mit einem Proxy, der die Transaktion um den Aufruf herum öffnet und schließt. Alles, was die Methode tut, einschließlich der Aufrufe des DAO, findet in derselben Transaktion und auf derselben Verbindung statt;
    • Zeilen 32–35: [readOnly = true]: eine schreibgeschützte Transaktion, die [Hibernate] davon befreit, am Ende geänderte Entitäten prüfen zu müssen;
    • Zeilen 37–40: Eine nicht vorhandene Person ist eine [BusinessException]. [orElseThrow] gibt den Inhalt des [Optional] zurück oder löst die vom Lambda erzeugte Exception aus, wenn er leer ist;
    • Zeilen 42–48: das Hinzufügen. Regel: Keine zwei Personen dürfen denselben Vor- und Nachnamen haben. Dies wird vor dem Schreiben geprüft, um eine klare Meldung anzuzeigen. Keine Person hat die ID 0: [IdNot] schließt hier niemanden von der Suche aus;
    • Zeilen 50–64: die Aktualisierung. Zusätzliche Regel: die optimistische Sperre (Zeilen 53–55). Das Aktualisierungsformular verwendet die Version des Datensatzes, wie sie beim Öffnen des Formulars war. Hat sie sich inzwischen geändert (ein anderer Benutzer hat denselben Datensatz bearbeitet), wird die Aktualisierung abgelehnt, statt die Arbeit des Benutzers stillschweigend zu überschreiben. [Objects.equals] vergleicht zwei [Integer]-Instanzen und akzeptiert dabei [null];
    • Zeile 51: Der Aufruf von [read] ist ein interner Aufruf innerhalb der Klasse: Er läuft nicht über den Proxy, und sein [readOnly] greift nicht. [read] wird einfach in der Transaktion von [edit] ausgeführt;
    • Zeilen 60–63: Die in der Transaktion gelesene Entität wird von [Hibernate] verfolgt (man sagt, sie sei „verwaltet“): Ändern Sie einfach ihre Felder; [Hibernate] erkennt die Änderungen und erzeugt ein [UPDATE] für die Spalten der Tabelle;
    • Zeilen 66–70: das Löschen. Die Person wird zuerst gelesen – um zu prüfen, dass sie existiert, und damit der Controller ihren Namen erwähnen kann;
    • Zeilen 74–87: das Speichern. Normalerweise sendet [Hibernate] die Befehle [INSERT] und [UPDATE] erst am Ende der Transaktion an die Datenbank, beim [COMMIT], d. h. nach dem Verlassen der Methode: Ein Datenbankfehler könnte hier nicht mehr abgefangen werden. [saveAndFlush] speichert die Entität und sendet sofort ([flush]) die ausstehenden SQL-Befehle;
    • Zeilen 77–79: Die zuvor erwähnte Versionsprüfung genügt nicht immer: Zwei Benutzer können denselben Datensatz gleichzeitig speichern, und beide bestehen die Prüfung. Das [UPDATE ... WHERE id = ? AND version = ?] des zweiten Benutzers ändert dann keine Zeile; [Hibernate] erkennt dies, und [Spring] löst eine [ObjectOptimisticLockingFailureException] aus, die zu derselben [BusinessException] wird;
    • Zeilen 80–85: Ebenso bestehen zwei gleichzeitige Hinzufügungen derselben Person die Namensprüfung, doch die Eindeutigkeitsbedingung der Datenbank lässt nicht zu, dass beide akzeptiert werden. [Spring] übersetzt die Exceptions der verschiedenen Datenbanken und der verschiedenen ORMs in eine gemeinsame Exception-Hierarchie: Eine Verletzung einer Bedingung wird zu einer [DataIntegrityViolationException]. [getMostSpecificCause()] liefert die ursprüngliche Exception – die des [MySQL]-Treibers –, deren Meldung den Namen der verletzten Bedingung nennt ([Duplicate entry '...' for key 'unq_persons_first_name_last_name']). Eine andere Verletzung einer Bedingung wird weitergereicht (Zeile 85): Das ist eine Anomalie.

    In allen Fällen, in denen eine Exception eine Methode von [PersonsBusiness] verlässt (einschließlich [BusinessException], da sie von [RuntimeException] erbt), rollt der Proxy die Transaktion zurück: Keine der Aktionen der Methode bleibt erhalten. Hinweis: Standardmäßig löst eine geprüfte Exception (die von [Exception] erbt, ohne von [RuntimeException] zu erben) kein Rollback aus.

    Diesen letzten Fall haben wir überprüft, indem wir 30 Anfragen gleichzeitig sendeten, um dieselbe Person hinzuzufügen: Nur eine wurde akzeptiert; bei den anderen lehnte die Datenbank das [INSERT] ab (Fehler [MySQL] Nr. 1062, den [Hibernate] in der Konsole als Warnung [HHH000247] meldet), und der Benutzer erhielt die Meldung zum Namensduplikat, keinen 500-Fehler.

    package example28.controllers;

import org.springframework.beans.propertyeditors.StringTrimmerEditor;
import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.validation.BindingResult;
import org.springframework.web.bind.WebDataBinder;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.InitBinder;
import org.springframework.web.bind.annotation.ModelAttribute;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.servlet.mvc.support.RedirectAttributes;

import example28.entities.Person;
import example28.business.PersonData;
import example28.business.BusinessException;
import example28.business.PersonsBusiness;
import example28.models.PersonForm;
import jakarta.validation.Valid;

// die WEB-Schicht: sie kennt nur die Geschäftsschicht
@Controller
public class PersonsController {

    private final PersonsBusiness business;

    public PersonsController(PersonsBusiness business) {
        this.business = business;
    }

    // von den empfangenen Strings werden überflüssige Leerzeichen entfernt (siehe Beispiel 19)
    @InitBinder
    public void initBinder(WebDataBinder binder) {
        binder.registerCustomEditor(String.class, new StringTrimmerEditor(true));
    }

    @GetMapping("/")
    public String home() {
        return "redirect:/persons";
    }

    @GetMapping("/persons")
    public String list(Model model) {
        model.addAttribute("persons", business.list());
        return "persons/list";
    }

    @GetMapping("/persons/add")
    public String addForm(Model model) {
        return form(model, "Add a person", "/persons/add", new PersonForm(), null);
    }

    @PostMapping("/persons/add")
    public String add(@Valid @ModelAttribute("person") PersonForm input, BindingResult result,
            Model model, RedirectAttributes redirect) {
        if (result.hasErrors()) {
            return form(model, "Add a person", "/persons/add", input, null);
        }
        try {
            Person p = business.add(new PersonData(input.getFirstName(), input.getLastName(), input.getAge()));
            redirect.addFlashAttribute("success", p.getFirstName() + " " + p.getLastName() + " has been added.");
            return "redirect:/persons";
        } catch (BusinessException e) {
            // eine Geschäftsregel lehnt ab: wir zeigen das Formular erneut an, die Meldung am Seitenende
            return form(model, "Add a person", "/persons/add", input, e.getMessage());
        }
    }

    @GetMapping("/persons/{id:\\d+}/edit")
    public String editForm(@PathVariable int id, Model model, RedirectAttributes redirect) {
        try {
            Person p = business.read(id);
            PersonForm values = new PersonForm();
            values.setFirstName(p.getFirstName());
            values.setLastName(p.getLastName());
            values.setAge(p.getAge());
            values.setVersion(p.getVersion());
            return form(model, "Edit a person", "/persons/" + id + "/edit", values, null);
        } catch (BusinessException e) {
            redirect.addFlashAttribute("error", e.getMessage());
            return "redirect:/persons";
        }
    }

    @PostMapping("/persons/{id:\\d+}/edit")
    public String edit(@PathVariable int id, @Valid @ModelAttribute("person") PersonForm input,
            BindingResult result, Model model, RedirectAttributes redirect) {
        String action = "/persons/" + id + "/edit";
        if (result.hasErrors()) {
            return form(model, "Edit a person", action, input, null);
        }
        try {
            PersonData data = new PersonData(input.getFirstName(), input.getLastName(), input.getAge());
            Person p = business.edit(id, input.getVersion(), data);
            redirect.addFlashAttribute("success", p.getFirstName() + " " + p.getLastName() + " has been edited.");
            return "redirect:/persons";
        } catch (BusinessException e) {
            return form(model, "Edit a person", action, input, e.getMessage());
        }
    }

    @PostMapping("/persons/{id:\\d+}/delete")
    public String delete(@PathVariable int id, RedirectAttributes redirect) {
        try {
            Person p = business.delete(id);
            redirect.addFlashAttribute("success", p.getFirstName() + " " + p.getLastName() + " has been deleted.");
        } catch (BusinessException e) {
            // kein Formular erneut anzuzeigen: der Fehler reist ebenfalls als Flash-Attribut
            redirect.addFlashAttribute("error", e.getMessage());
        }
        return "redirect:/persons";
    }

    // das Modell der Formular-View: Titel, Zieladresse zum Senden, Werte, globaler Fehler
    private String form(Model model, String title, String action, PersonForm values, String error) {
        model.addAttribute("title", title);
        model.addAttribute("action", action);
        model.addAttribute("person", values);
        model.addAttribute("error", error);
        return "persons/form";
    }
}
